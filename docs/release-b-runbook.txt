## 1. Pre-checks — all must come back clean

```bash
# 1a. Advisory locks. pg_advisory_lock(bigint) splits the 64-bit key into
# pg_locks.classid (high 32 bits) + objid (low 32 bits) — comparing objid
# alone can NEVER match any of these three keys, since all three exceed
# 2^32 (4294967296) and so always have a nonzero classid. Reconstruct the
# original key instead:
docker exec ara-dashboard-prod sh -c 'psql "$POSTGRES_URL" -c "SELECT ((classid::bigint << 32) | objid::bigint) AS lock_key, pid, granted FROM pg_locks WHERE locktype='"'"'advisory'"'"';"'
# Keys: 7482910234 = Lateral job, 7482910249 = Executive job,
# 7482910263 = candidate purge job (unchanged by this release — confirmed via
# grep against src/lib/persistence/job-lock.ts). Any row = one of those is
# mid-flight — wait for it, don't deploy over it.

# 1b. No Oorwin upload/replay mid-flight (generic pre-deploy safety gate,
# unrelated to this release's own code, but the container restart below
# would kill it mid-flight regardless of which feature is being shipped).
docker exec ara-dashboard-prod sh -c 'psql "$POSTGRES_URL" -c "SELECT id, kind, started_at FROM candidate_sync_history WHERE finished_at IS NULL;"'

# 1c. No active query touching the tables this release's logic reads/writes
# (pid/state/duration only — never query text). Excludes pg_backend_pid() so
# the check doesn't match its own psql session.
docker exec ara-dashboard-prod sh -c 'psql "$POSTGRES_URL" -c "SELECT pid, state, now() - query_start AS running_for FROM pg_stat_activity WHERE pid <> pg_backend_pid() AND (query ILIKE '"'"'%lateral_scheduler_state%'"'"' OR query ILIKE '"'"'%lateral_sync_history%'"'"' OR query ILIKE '"'"'%gmail_checkpoint%'"'"') AND state <> '"'"'idle'"'"';"'
```
Quoting of all three `-c "..."` SQL strings above was tested locally with
`psql` swapped for `echo` (no docker, no prod) — each resolves to exactly
the intended single SQL statement, correctly single-quoted
(`locktype='advisory'`, the three `ILIKE '%...%'` patterns, `state <>
'idle'`). Not re-tested against the real container/DB.

## 4. Backup — OPTIONAL for this release, take one anyway

This release has **no migration and no schema change** — rollback (section 9)
is a pure image retag + container recreate, with zero data-shape risk; there
is nothing a restore would ever need to undo that a retag doesn't already
fix. Strictly required: **no**. Recommended anyway: **yes** — it's cheap,
and a backup immediately before any prod container restart is generically
good practice independent of what the release itself touches (the restart
below briefly stops the running process regardless).

```bash
docker exec ara-dashboard-prod pg_dump --version
```
If that errors or prints nothing, STOP before the backup step below.

```bash
df -h /root
mkdir -p /root/release-b-backups && chmod 700 /root/release-b-backups
( umask 077
  docker exec ara-dashboard-prod sh -c 'pg_dump -Fc "$POSTGRES_URL"' \
    > /root/release-b-backups/pre-release-b-20261009.dump )
head -c 5 /root/release-b-backups/pre-release-b-20261009.dump; echo   # expect PGDMP
ls -la /root/release-b-backups/pre-release-b-20261009.dump            # non-empty
docker exec -i ara-dashboard-prod pg_restore -l < /root/release-b-backups/pre-release-b-20261009.dump | head
```
This dump contains candidate data (same database as everything else) —
handle like any other PII dump, delete it by its exact name once the release
is confirmed good.

## 6. Timing — do not deploy or click during these windows

- Not on a weekday between 10:00–14:00 IST unless step 1 is clean right
  before you start.
- Not around 03:00 IST — the candidate purge job runs then and holds its
  own advisory lock (7482910263).
- After deploy, avoid clicking Run All on Lateral/Executive during the
  `:55`–`:05` minute window of any hour inside 10:00–14:00 IST — a
  scheduled Run All is most likely to be running then and holds the same
  per-dataset advisory lock (not independently re-verified against today's
  actual cron schedule — confirm the real schedule before relying on this).
